# AstraeaOS WP — Password Security & Migration Specification

**Distribution:** AstraeaOS WP `0.1.0-alpha`  
**Primary Algorithm:** `PASSWORD_ARGON2ID` (RFC 9106)  
**Legacy Migration Strategy:** Verify Legacy → Rehash Modern  

---

## 1. Core Principles

1. **Passwords Are Never Encrypted:** Passwords are strictly hashed with a slow, memory-hard algorithm. Reversible encryption is forbidden.
2. **GPU & ASIC Cracking Resistance:** Argon2id requires significant RAM (default 64 MB per calculation), starving high-speed parallel cracking rigs of bandwidth.
3. **Zero Static Salts:** Each password hash receives an individualized, cryptographically secure 128-bit salt generated by the operating system CSPRNG.
4. **Transparent Migration:** Existing user passwords are never invalidated. Users log in seamlessly with their historic passwords, which are converted to Argon2id in the same millisecond.

---

## 2. Active Argon2id Policy

AstraeaOS WP enforces guarded adaptive parameters configured in `Astraea\Auth\Argon2idPolicy`:

| Parameter | Default | Safe Lower Bound | Safe Upper Bound | Rationale |
| :--- | :--- | :--- | :--- | :--- |
| **`memory_cost`** | `65536` (64 MB) | `16384` (16 MB) | `262144` (256 MB) | Enforces memory hardness without causing out-of-memory errors on shared hosting. |
| **`time_cost`** | `4` iterations | `2` iterations | `10` iterations | Balances CPU time budget against brute-force work factor. |
| **`threads`** | `1` lane | `1` lane | `4` lanes | Prevents thread contention under high concurrent authentication load. |

### Administrative Overrides (`wp-config.php`):
```php
define('ASTRAEA_ARGON2ID_MEMORY', 65536);
define('ASTRAEA_ARGON2ID_TIME', 4);
define('ASTRAEA_ARGON2ID_THREADS', 1);
```
All parameters are clamped against enforced bounds to prevent accidental denial-of-service configuration mistakes.

## 3. "Verify Legacy → Rehash Modern" Protocol

The migration sequence occurs entirely within `Astraea\Auth\PasswordMigrationManager`:

```
[ User Submits Login (Username, Password) ]
                    │
                    ▼
[ PasswordService::verify($password, $hash) ]
                    │
         ┌──────────┴──────────┐
         ▼                     ▼
[ Hash Format Check ]     [ Password Invalid ]
         │                     │
         ├─ $argon2id$         ▼
         │   (Modern)    [ Reject Login ]
         │
         ├─ $wp$2y$ (WP 6.8+ Bcrypt)
         ├─ $2y$ (Standard Bcrypt)
         ├─ $P$ / $S$ (phpass)
         └─ 32-char Hex (Pre-WP 2.5 MD5)
                    │
                    ▼
[ Verify via LegacyHashVerifier ]
                    │
         ┌──────────┴──────────┐
         ▼                     ▼
   [ Valid Match ]      [ Invalid Match ]
         │                     │
         ▼                     ▼
[ PasswordService::needsRehash() === true ]
         │
         ▼
[ PasswordService::hash($password) ]
   (Generate new $argon2id$ hash with individual salt)
         │
         ▼
[ Atomic Database Update: wp_users.user_pass ]
         │
         ▼
[ Issue Authenticated Session & Log Migration Audit Event ]
```

## 4. Optional Server-Side Pepper

AstraeaOS supports an optional server-side secret pepper (`ASTRAEA_PASSWORD_PEPPER`) for defense-in-depth against complete database exfiltration.

### Storage Rules:
- **FORBIDDEN:** Storing the pepper in MySQL/MariaDB options, user meta, source code, git repositories, or themes.
- **PERMITTED:** 
  1. Environment variable: `ASTRAEA_PASSWORD_PEPPER="<high_entropy_secret>"`
  2. Protected configuration file outside webroot: `define('ASTRAEA_PASSWORD_PEPPER_FILE', '/etc/astraea/pepper.key');`

### Cryptographic Application:
Before being passed to `password_hash()` or `password_verify()`, the password is pre-hashed using keyed HMAC-SHA384:
$$\text{pre\_hash} = \text{base64}(\text{HMAC-SHA384}(\text{password}, \text{pepper}))$$

### Operational Consequences of Pepper Loss or Rotation:
> [!CAUTION]
> **Loss of Pepper:** If a configured pepper is deleted or lost, all existing peppered hashes become unverifiable. Users will need to reset passwords via email recovery or WP-CLI.
>
> **Rotation Procedure:** To rotate a pepper, configure the new pepper while retaining fallback verification for the previous pepper, allowing users to migrate to the new pepper during their next login.
